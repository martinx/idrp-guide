# 00 前言与总体架构

## 0.1 我们要解决的问题

假设你负责一个软件产品，产品经理/研发团队每周都会交付若干"功能点"（feature point）：新增一个设置项、修复一个交互、上线一个仪表盘卡片。传统的做法是：

1. 有人手动打开产品，操作一遍功能；
2. 用屏幕录制软件录下来；
3. 自己配一段解说词，或者干脆不配音，只加字幕；
4. 剪辑软件里拼接封面、加转场、导出；
5. 上传到内部 wiki / 客户培训平台 / 销售演示库。

这个流程有几个致命问题：

- **不可复用**：功能一旦有 UI 微调，整个视频要重录、重剪。
- **人力密集**：每个功能点视频背后是 30 分钟到 2 小时的人工操作。
- **质量不稳定**：不同人录制的节奏、解说风格、封面样式都不统一。
- **无法规模化**：一个季度几十个功能点，人工根本跟不上。

我们希望达到的目标状态是：

> 工程师/产品经理只需要写一句话描述"这个功能点做什么、有哪些关键操作步骤"，
> 再手动操作一遍浏览器（这一遍会被 codegen 自动记录成脚本），
> 之后一个命令，就能得到一条**带解说配音、带字幕、带封面、成品分辨率/码率达标**的功能演示视频。

这就是本教程要从零构建的系统。全书称之为 **"意图驱动录制流水线"**（Intent-Driven Recording Pipeline，下文简称 IDRP）。

## 0.2 设计哲学：三个"最小化"

1. **最小化人工描述**：人只需要提供"意图"——这个功能是什么、大致步骤是什么、每一步要强调什么。意图用一个结构化但轻量的 YAML 文件（Feature Spec）表达，见第 03 章。
2. **最小化人工操作**：真正需要人手动做的事情只有一件——在浏览器里把这个功能点操作一遍，供 codegen 录制成自动化脚本。除此之外不需要人工剪辑、配音、调时间轴。
3. **最小化人工介入后续环节**：录制、配音、封面、合成、导出全部由程序编排完成，人工只在最后审片环节介入（这一环节按第 10 章的检查清单执行）。

## 0.3 系统总体架构

整个流水线由五个核心能力模块 + 一个编排器组成：

```
                        ┌─────────────────────────┐
                        │   Feature Spec (YAML)    │   人工编写，描述"意图"
                        │  - 功能名/步骤/解说文案   │
                        └────────────┬─────────────┘
                                     │
                 ┌───────────────────┼────────────────────┐
                 ▼                   ▼                    ▼
        ┌─────────────┐     ┌───────────────┐     ┌───────────────┐
        │  Codegen 层  │     │   Dub 层       │     │  Cover 层      │
        │ (Playwright  │     │ (TTS 配音 +    │     │ (HTML 模板     │
        │  codegen 录制│     │  时长测算)     │     │  截图生成封面) │
        │  出交互脚本) │     │               │     │               │
        └──────┬───────┘     └───────┬───────┘     └───────┬───────┘
               │                     │                     │
               ▼                     │                     │
        ┌─────────────┐              │                     │
        │  Record 层   │              │                     │
        │ (自动化脚本  │              │                     │
        │  驱动浏览器  │              │                     │
        │  +屏幕录制)  │              │                     │
        └──────┬───────┘              │                     │
               │                     │                     │
               └──────────┬──────────┴──────────┬──────────┘
                          ▼                     ▼
                  ┌──────────────────────────────────┐
                  │        Mix 层 (ffmpeg 合成)        │
                  │  拼接分段视频 + 混音 + 字幕烧录 +  │
                  │  封面片头 + 响度归一化 + 导出规范  │
                  └──────────────────┬─────────────────┘
                                     ▼
                          ┌─────────────────────┐
                          │     成片 .mp4        │
                          └─────────────────────┘
```

对照到具体章节：

| 模块 | 对应章节 | 一句话职责 |
|---|---|---|
| Feature Spec | 03 | 把"意图"结构化为机器可读的步骤列表 |
| Codegen 层 | 04 | 把"人手动操作一遍"转成可重放的自动化脚本 |
| Record 层 | 05 | 重放脚本的同时，把屏幕/浏览器画面录制成分段视频 |
| Dub 层 | 06 | 把每一步的解说文案转成配音音频，并反向决定每一步该"停留"多久 |
| Cover 层 | 07 | 生成片头封面图/片段 |
| Mix 层 | 08 | 把分段视频、配音、字幕、封面按时间轴合成为一条成片 |
| 编排器 | 09 | 一个命令把以上全部串起来 |

## 0.4 为什么是"音频先行"而不是"视频先行"

这是整个系统里最关键的设计决策，值得在前言里先讲清楚，后面各章会反复引用。

如果你先录制视频、再配音，你会遇到一个几乎无解的问题：**解说词的长度和操作节奏很难精确匹配**。人配音时语速会变化，操作录制时点击间隔也会变化，两条时间轴对不上，最后只能靠剪辑软件手动拉伸/裁剪音频或视频，效率低且不可自动化。

反过来，如果**先确定每一步的解说文案 → 用 TTS 生成音频 → 用 ffprobe 测出每段音频的精确时长 → 把这个时长喂给自动化脚本，让它在对应步骤"等待"这么久**，那么视频的节奏就会天然地和配音对齐，因为视频的时长是被音频时长"驱动"出来的，而不是反过来去凑。

这也是为什么 Feature Spec（03 章）里，解说文案是第一位的、结构化的字段，而不是录制完之后才补充的东西。

## 0.5 技术选型一览（详细理由见各章）

| 能力 | 选型 | 备选 |
|---|---|---|
| 浏览器自动化/录制 | Playwright（Node.js / TypeScript） | Puppeteer、Selenium |
| 屏幕级录制（终端等非浏览器画面） | ffmpeg + 平台原生采集设备（avfoundation/x11grab/gdigrab） | OBS Studio + WebSocket 远程控制 |
| TTS 配音 | 云端 TTS（如 Azure/阿里云/腾讯云语音合成）为主，离线 TTS（macOS `say` / edge-tts）为兜底与本地开发调试 | Coqui TTS 本地模型 |
| 封面生成 | Headless 浏览器截图 HTML/CSS 模板 | Canvas/ImageMagick 直接绘制 |
| 音视频合成 | ffmpeg | Remotion（React 渲染视频，适合更强的动画需求） |
| 编排语言 | TypeScript（与 Playwright 生态一致） | Python（如果团队已有更强 Python 生态） |
| 配置格式 | YAML（Feature Spec） | JSON、TOML |

后续章节会逐一展开每个模块的原理、代码实现和踩坑点。建议按顺序阅读，因为 03 章定义的 Feature Spec 结构会贯穿全书所有代码示例。

## 0.6 团队角色分工建议

即使是一个人独立搭建和使用这套系统，明确"哪个环节该由谁、以什么身份完成"也有助于理解整体设计。如果是多人团队协作，建议按下面的角色划分：

- **需求提出方（通常是产品经理）**：只负责提供 00 章开篇提到的"一句话意图 + 粗粒度步骤"，不需要接触 Feature Spec 的 YAML 语法，也不需要理解任何本教程后续的技术实现。
- **录制工程师（通常是前端/测试/自动化工程师）**：负责把意图扩写成完整 Feature Spec（03 章）、执行 codegen 录制和脚本清洗（04 章）、首次跑通并微调节奏（09 章）、执行录制前后的检查清单（10 章）。这是本教程主要面向的角色。
- **系统维护者（通常是团队里对这套流水线本身负责的 1～2 名工程师）**：负责环境和依赖的升级维护（01 章）、公共 codegen 片段库的治理（02 章 2.7 节）、CI 集成和性能优化（11 章）、以及在功能点数量增长后重新评估投入策略（14 章）。在团队规模较小时，这个角色和"录制工程师"可以是同一个人；规模扩大后建议明确分离，避免系统维护职责在多人之间"三个和尚没水吃"。
- **审片人（可以是录制工程师本人，也可以是团队里指定的另一人）**：负责 10 章的最终审片环节。如果条件允许，建议审片人和录制工程师不是同一人——旁观者更容易发现录制者本人因为"看惯了"而忽略的问题（比如 10.6 节提到的菜单栏常驻组件，录制者自己每天都看到反而不会注意，换一双眼睛更容易发现）。

这个角色划分不是强制的组织架构要求，而是帮助厘清"这套系统运转起来，到底需要哪些不同性质的判断和操作"，具体到某个团队，可以按实际人力灵活合并或拆分这些角色。
