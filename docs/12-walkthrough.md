# 12 端到端实战演练：从一句话到一条成片

前面 11 章分模块讲清楚了原理和代码，本章把所有环节串起来，完整走一遍"从产品经理提出一句话需求，到最终拿到一条可以对外发布的成片"的真实工作流程，包含每一步实际会看到的输出、可能遇到的中间状态、以及每个角色（产品经理/工程师/审片人）分别要做什么。假设我们要做的功能点是本书反复引用的例子："报表导出功能"。

## 12.1 第 0 天：需求提出

产品经理在需求评审会上确认了一个新功能已经上线到 staging 环境：用户在报表页面可以一键导出 Excel。需要制作一条演示视频放进产品培训库。产品经理不需要懂任何技术细节，只需要在共享文档里写下一句话：

> "报表页面加了导出功能，用户选好时间范围和维度后点导出，能选 Excel 格式，导出的时候有进度条，做个演示视频。"

这句话，加上产品经理顺手截的三张页面截图（报表页、导出按钮、导出进度弹窗），就是本次录制任务的全部原始输入。对照 00 章的设计哲学，这正是"最小化人工描述"要达到的效果——需求方完全不需要学习 Feature Spec 的 YAML 语法。

## 12.2 第 1 天上午：工程师起草 Feature Spec 骨架

负责录制的工程师打开 `specs/` 目录，参考 03 章 3.4 节的"两步法"，先写一份最简骨架：

```yaml
id: feature-07-export-report
title: 报表导出功能
intent: 用户在报表页面一键导出 Excel，带进度提示。
steps_outline:
  - 进入报表页面，选时间范围和维度
  - 点击导出按钮，弹出格式选择
  - 选 Excel 确认，显示进度直到完成
```

这一步耗时大约 5 分钟——工程师只是把产品经理的一句话拆成了三个粗粒度步骤，没有涉及任何选择器、时长、配音细节。

## 12.3 第 1 天上午：用 LLM 辅助扩写为完整 Spec

工程师把上面的骨架和 03 章 3.2 节的完整字段模板一起交给 LLM 工具，得到扩写后的完整 Feature Spec（也就是 03 章 3.2 节展示的那份完整 YAML）。这一步 LLM 输出通常是"可用但需要微调"的状态——常见需要人工调整的地方包括：

- 解说文案的语气略微书面化，需要按团队实际口语习惯改得更自然一点，比如把"系统会弹出导出格式选择"改成"点击后会弹出一个选择框，可以选导出格式"。
- LLM 猜测的 `codegen_ref` 命名有时和团队既有片段库命名习惯不一致（比如 LLM 写成 `clickExportButton`，团队约定是 kebab-case 的 `click-export-button`），需要手动改一下大小写风格。
- `pace.min_hold_sec` 的初始值是 LLM 按经验给的估计值，后续会在录制过程中根据实际观感微调。

这一步耗时大约 15～20 分钟，产出就是可以直接拿去下一步的完整 `feature-07-export-report.yaml`。

## 12.4 第 1 天下午：Codegen 录制操作片段

工程师按照 04 章 4.2 节的流程，依次为三个 `action` 步骤各录一次 codegen 会话：

```bash
npx playwright codegen --viewport-size=1440,900 \
  --output=src/codegen/raw/open-report-page.raw.ts \
  https://staging.example.com/reports
```

实际操作中，工程师打开报表页，点开时间范围选择器选"最近30天"，点开维度下拉选"按渠道"，然后关闭 codegen 窗口。Inspector 面板里实时生成的代码大致是：

```typescript
await page.getByRole('link', { name: '报表' }).click();
await page.getByLabel('时间范围').click();
await page.getByText('最近30天').click();
await page.getByLabel('数据维度').selectOption('按渠道');
```

这段代码基本是干净的（因为操作本身很克制，没有误点），工程师只需要按 4.3 节的清洗流程，把它包装成具名函数存进 `src/codegen/steps/open-report-page.ts`，不需要额外改动逻辑。

对第二个步骤"点击导出按钮"和第三个步骤"选 Excel 确认"重复同样的流程,分别产出 `click-export-button.ts` 和 `choose-excel-confirm.ts`。第三个步骤因为涉及"等待导出完成"这个异步状态，工程师额外在清洗后的脚本里保留了一个显式等待：

```typescript
export async function chooseExcelConfirm(page: Page): Promise<void> {
  await page.getByText('Excel').click();
  await page.getByRole('button', { name: '确认' }).click();
  await page.getByText('导出完成').waitFor({ state: 'visible', timeout: 15000 });
}
```

三个片段全部清洗完成，耗时大约 40 分钟（含反复调试选择器）。

## 12.5 第 1 天下午：冒烟测试

按 04 章 4.6 节的方法，工程师跑一遍三个片段的 headless 冒烟测试：

```bash
ts-node src/codegen/steps/__smoke__/open-report-page.smoke.ts
ts-node src/codegen/steps/__smoke__/click-export-button.smoke.ts
ts-node src/codegen/steps/__smoke__/choose-excel-confirm.smoke.ts
```

第一次运行,`choose-excel-confirm` 冒烟测试超时失败——控制台报错：

```
Error: page.waitForSelector: Timeout 15000ms exceeded.
=========================== logs ===========================
waiting for getByText('导出完成') to be visible
============================================================
```

排查发现,实际页面上进度完成后的提示文案是"导出成功"而不是"导出完成"（工程师此前是凭记忆写的，和产品经理的截图核对后确认了准确文案）。修正选择器文案后重新跑冒烟测试，三个片段全部通过。这个例子说明了 4.6 节"冒烟测试要在正式录制前跑"的价值——如果没有这一步，这个错误会在后面 09 章编排器的 Preflight 阶段才被发现，或者更糟糕的情况是在真正的录制过程中才发现，浪费的时间成本高得多。

## 12.6 第 2 天上午：审阅解说文案与配置

工程师和产品经理一起过一遍 Feature Spec 里的 `narration` 文案，确认语气和用词，同时按 01 章、07 章确认好的团队规范填好 `output` 字段（分辨率 1920x1080，字幕烧录，暂不加背景音乐）。这一步也顺带执行了 10 章 10.2 节"录制前检查清单"里"文案审阅"这一项。

## 12.7 第 2 天上午：跑通完整流程（首次，人工旁站）

按 10 章 10.3 节的建议，首次为这个新 Feature Spec 跑流程时全程旁站观察：

```bash
npm run run:feature -- specs/reports/feature-07-export-report.yaml
```

控制台日志大致是这样滚动的：

```
[feature-07-export-report] 开始处理: 报表导出功能
[feature-07-export-report] Preflight 检查...
[feature-07-export-report] 生成配音...
[feature-07-export-report] 生成封面...
[feature-07-export-report] 执行操作并录制...
[feature-07-export-report] 拼接分段...
[feature-07-export-report] ✅ 完成: output/feature-07-export-report.mp4
```

整个过程耗时约 3 分钟（其中配音生成因为用的是云端 TTS，网络请求占了大部分时间；操作录制本身因为只有三步、每步几秒钟停留，耗时很短）。旁站过程中工程师注意到"点击导出按钮"这一步画面停留略短，配音刚讲完画面就切走了，回头检查发现是这一步没有设置弹窗动画的等待，弹窗展开动画比配音时长稍长导致视觉上略显仓促。工程师在 Spec 里把该步骤的 `pace.min_hold_sec` 从 2 调到 2.5，重新跑一遍，问题解决。

## 12.8 第 2 天下午：审片

按 10 章 10.4 节的清单完整播放一遍成片：封面标题正确、三步操作画面清晰、配音与画面同步、字幕正确、音量均匀、`ffprobe` 核对分辨率码率符合预期、没有发现任何敏感信息（因为使用的是脱敏演示账号 + staging 环境）。审片通过，成片正式发布到产品培训库。

## 12.9 从需求提出到发布的总耗时统计

| 阶段 | 参与角色 | 耗时 |
|---|---|---|
| 需求提出（一句话+截图） | 产品经理 | 5 分钟 |
| Spec 骨架 + LLM 扩写 | 工程师 | 20 分钟 |
| Codegen 录制三个片段 + 清洗 | 工程师 | 40 分钟 |
| 冒烟测试与修正 | 工程师 | 15 分钟 |
| 文案审阅 | 工程师+产品经理 | 15 分钟 |
| 首次跑通+微调 | 工程师 | 15 分钟 |
| 审片 | 工程师 | 10 分钟 |
| **合计** | | **约 2 小时** |

对比传统人工录制+剪辑一条同等质量演示视频通常需要的 1.5～3 小时纯手工操作（且大部分是不可复用的一次性劳动），这套流水线的时间投入主要集中在"一次性建立 Spec 和 codegen 片段"上，而这部分投入在功能后续小幅迭代（比如只是按钮文案改了个字）时几乎可以完全复用——只需要重新录一下变化的那个 codegen 片段，重新跑一遍编排器即可，不需要重新走完整的两小时流程。这是这套系统真正的规模化收益所在：**首次投入不比人工录制快多少，但第二次、第三次维护同一个功能点的视频时，成本会指数级下降**。

## 12.10 一次典型的"维护性重录"场景

三个月后，产品对导出按钮的文案从"导出"改成了"导出报表"，且弹窗位置从右上角挪到了页面中间。工程师需要做的事情是：

1. 重新对 `click-export-button` 这一个 codegen 片段单独录制（因为按钮文案变了，选择器 `getByRole('button', { name: '导出' })` 需要改成 `{ name: '导出报表' }`）——大约 5 分钟。
2. 冒烟测试通过后，`narration` 文案本身不需要改（解说词说的是"点击导出按钮"，这个语义没变），Feature Spec 文件几乎不需要动。
3. 重新跑一遍编排器，因为其他两个片段和所有配音文案都没变化，如果按 11 章 11.2 节配置了配音/封面的内容哈希缓存，这一次运行会跳过重新调用 TTS API，只重新录制变化的那一段画面并重新拼接、导出。
4. 快速审片确认新画面正确，发布。

整个维护性重录耗时约 15～20 分钟，这正是"意图驱动 + 最小化 codegen"架构设计要追求的长期收益。
